Six ways to give the library a spine

Right now every video lands in one undifferentiated list. This report lays out six organizing models — from "do almost nothing" to "no vocabulary at all" — with honest trade-offs, the Pocketbase schema each needs, and a clickable mock-up of each so you can feel it before you commit.

00 · Where you actually are

Facts pulled from the codebase, not assumptions — these constrain every option below.

Schema
videos has url, video_id, title, status, slides_html, deck, transcript, error. There is no tags field, no channel field, no collection field.
The rail
FilterRail.tsx renders a SUBSCRIPTIONS header over CHANNELS from src/data.ts — one hardcoded sample channel. It filters on video.channelId, which recordToVideo() always sets to null. So the rail is decorative today.
Dead fields
recordToVideo() hardcodes tags: [], starred: false, status: 'unread', readingTime: 0. The UI already renders tag pills and star buttons — the wiring is what's missing, not the components.
Filtering
One useMemo in App.tsx: substring match on title / tldr / tags, plus channel. Sort is fixed to publishedAt desc.
The AI hook
gemini.py already does one generate_content call per add with response_mime_type="application/json". Adding classification is either one extra field on the deck schema or one extra cheap call. The transcript and the generated tldr are both sitting right there.
The load-bearing observation

Because tags doesn't exist in the DB yet, every option below costs a migration anyway. There's no "cheap because it reuses what's there" option — so pick on merit, not on perceived migration cost. The real cost differences are in UI surface area and in how much ongoing curation each model demands from you.

01 · Flat list, better filters

01

Do almost nothing, but do it well

effort Sno AIcontrol option

Keep the single list. Wire up the fields the UI already draws but the DB never fills: starred, a real read status, sort options, and a search box that actually searches deck body text, not just the title. The rail stops pretending to be subscriptions and becomes a set of fixed lenses: Inbox / Unread / Starred / Archive / All.

This is the honest baseline. It is worth taking seriously because a lot of "I can't find anything" is really "I have no way to mark something as dealt with", and that's a status problem, not a taxonomy problem.

Pros
  • Ships in an afternoon; two new fields, zero new collections.
  • Zero filing tax — you never make a categorization decision.
  • Solves the most common real complaint: "which of these have I already dealt with?"
  • Nothing to migrate away from later. Every other option builds on top of this, not instead of it.
Cons
  • Doesn't touch the actual stated problem — unrelated topics still interleave.
  • Search only helps when you already know what you're looking for. Browsing stays impossible.
  • At ~150 videos the archive is a wall of text you never revisit.
  • No answer to "show me everything I've saved about X".
VerdictNot sufficient alone — but you should do the status/star/sort part regardless of which option below you pick. It's a prerequisite, not a competitor.

02 · Shelves — every video gets exactly one home

02

Folders, essentially

effort S–MAI picks the shelfsingle-parent

A shelves collection; videos.shelf is a single relation. The rail becomes the shelf list. On add, Gemini gets the list of existing shelf names and picks one, or answers null → the video lands in Unshelved and you drag it somewhere. Optionally one level of nesting (AI / Agents).

// migration sketch
shelves:  name (text, unique)  ·  color (text)  ·  sort (number)
videos:   + shelf (relation → shelves, maxSelect 1, optional)
Pros
  • The mental model everyone already has. No explanation needed, ever.
  • Cheapest possible AI task: pick one label from a closed list of ~10. Near-zero hallucination surface.
  • Rail navigation is obvious and stable — the same eight things are always in the same place.
  • "Unshelved" is a natural inbox that self-empties as you file.
  • Counts per shelf give you an honest picture of what you actually watch.
Cons
  • The killer: a video about using LLMs for personal finance has one home and it's wrong. This is the documented reason folder systems fail for personal libraries.
  • You will start creating shelves to resolve ambiguity ("AI-Finance") and end up with 25 shelves and a new problem.
  • No cross-cutting axes: you can't ask "everything that's a conference talk" across shelves.
  • Re-filing is manual and nobody ever does it. Mistakes calcify.
  • Shelf granularity is a decision you have to get right early and can't cheaply revise.
VerdictTempting for its simplicity, and genuinely fine if your topics are truly disjoint. Given you described "completely different topics" that might actually hold — but the first crossover video will annoy you permanently.

03 · Flat tags with AI suggest-then-confirm

03

Many tags per video, you confirm at add time

effort MAI suggestsmulti-label

A tags collection; videos.tags is a multi relation. On add, the backend sends Gemini the existing tag vocabulary with usage counts plus the freshly generated tldr, and asks for 2–4 tags — reusing existing ones wherever they fit and proposing new ones only when nothing does. The add dialog shows the suggestions as chips: existing ones pre-selected, newly invented ones visually distinct and requiring an explicit click before they're created.

That last distinction is the whole ballgame. Silent tag creation is how you get llm, LLMs, and large-language-models in the same library by week three.

tags:   name (text, unique)  ·  slug (text, unique)  ·  color (text)
videos: + tags (relation → tags, maxSelect 0 = unlimited)
Pros
  • Multi-topic videos are represented honestly — no forced single home.
  • Cross-cutting queries work: "interviews" ∩ "finance".
  • Vocabulary grows organically from what you actually watch instead of from a taxonomy you guessed at on day one.
  • Suggest-then-confirm keeps you in the loop at exactly the moment you have the most context — right after adding.
  • Cheap to retrofit: run the same tagger over your existing library in a batch job.
Cons
  • Tag sprawl. Without hygiene tools you land at 90 tags, 60 of which are used once. This is the single most documented failure mode of personal tagging systems.
  • Granularity drift: the model tags one video software and the next rust-async-runtimes. Nothing enforces a consistent altitude.
  • A flat tag list in the rail becomes unbrowsable past ~40 tags — you need a tag cloud, search, or sorting by count.
  • Adds a confirmation step to every add. Small, but it's friction you'll feel on video 200.
  • No "default view" — with no hierarchy the library has no shape when you open it cold.
VerdictThe right primitive, but on its own it lacks a backbone. It needs either hygiene tooling (§08) or a second tier (option 04) to stay usable past a hundred videos.

04 · Two-tier — one closed Topic, plus open tags

04

A fixed backbone with a soft surface

my recommendationeffort MAI does both tiers

Two distinct vocabularies with different rules:

  • Topic — a closed list of ~6–10 broad areas you define once (AI, Money, Craft, Body, History…). Every video gets exactly one. The model may not invent Topics; if nothing fits it must return null and the video goes to Unsorted. This gives the rail a stable, browsable shape forever.
  • Tags — an open multi-label set. The model reuses existing tags freely and may propose new ones, subject to your confirmation. This is where specificity and cross-cutting axes live.

The key insight: the two failure modes are opposite, and separating the tiers cancels them out. Folders fail because they're too rigid for a multi-topic item; tags fail because nothing constrains their growth. Here rigidity is applied only where it's cheap (a handful of stable Topics you rarely revisit) and freedom only where it's useful (specific tags that can be pruned without breaking navigation).

// one table, two kinds — see §09 for why this beats two separate collections
tags:   name (text, unique) · norm (text, unique) · kind ('topic'|'tag') · color · sort
videos: + topic (relation → tags, maxSelect 1, optional)
        + tags  (relation → tags, maxSelect 0)
        + tag_source (json)   // { "llm": "ai", "investing": "human", ... }

Prompt-side, this is one call returning {"topic": "AI", "topic_confidence": 0.9, "tags": [...], "new_tags": [...]} where topic is constrained by an enum in the response schema — Gemini's structured output can enforce that mechanically, so the closed list is guaranteed, not merely requested.

Pros
  • The rail is permanently browsable: eight entries, always the same, always in the same order. Cold-open shape.
  • Tag sprawl becomes harmless — sprawl in tier 2 doesn't degrade navigation, it only degrades a secondary filter you can prune whenever.
  • Multi-topic videos still work: crossover gets Topic: AI + tags: [investing, agents] and is findable from both directions.
  • The closed Topic list is enforceable at the API level via a response-schema enum. No hallucinated Topics, structurally.
  • Granularity drift is solved by construction: the model can't answer a Topic question with a niche label.
  • Cheap escape hatch — if a tag hits 20 uses, promote it to a Topic. The system tells you when your taxonomy is wrong.
Cons
  • Two concepts to explain and two UI surfaces to build. More code than 02 or 03 alone.
  • You have to seed the Topic list up front, and getting it wrong early is annoying (though re-topicking 40 videos is one batch job).
  • The "exactly one Topic" rule reintroduces a small amount of the folder problem — the crossover video's Topic is still a judgement call, it's just no longer the only signal.
  • Two relations means two expand params on every list query. Minor, but the PB queries get chattier.
  • Overkill if your library stays under ~50 videos.
VerdictBest effort-to-durability ratio for what you described. You get the browsable shape of folders and the honesty of tags, and the failure mode of each is contained by the other. It's also the only option where the system tells you your own taxonomy is drifting.

05 · Smart views — auto-tag silently, never file anything

05

The library organizes itself; you write the queries

effort M–LAI applies silentlyzero filing

Tags get applied automatically with no confirmation step at all — you never see the add dialog do anything except succeed. Organization happens after the fact, through saved views: a views collection storing a filter tree (tags contains X AND duration > 20m AND status = unread). The rail lists your views. Add a view whenever a need arises; delete it when it stops being useful.

This is the iTunes smart-playlist / Gmail-filter model applied to a video library. The bet is that retrieval is the real need and filing is a cost you pay for nothing.

Pros
  • Truly zero friction at add time — paste URL, done. Nothing else in this report is this frictionless.
  • Views are cheap and disposable. Wrong view? Delete it. No data was moved, nothing broke.
  • One video can appear in any number of views without contradiction.
  • Composes with everything: views work over Topics and tags if you also do 02/04.
  • Retroactive by nature — a new view instantly includes old videos, no re-filing pass.
Cons
  • Silent auto-apply means silent wrong tags. You only discover the mistagging when a view mysteriously has the wrong things in it, long after you've lost the context to fix it.
  • You're now maintaining query logic, not a library. That's a different and less pleasant kind of work.
  • A filter-builder UI is the most expensive thing in this report to build well.
  • Views drift out of sync with a growing vocabulary: a view pinned to llm silently misses everything the model later tagged agents.
  • No browsing affordance — you can't discover what's in your library, only query things you already suspect are there.
  • Contradicts your stated preference for explicit choice at the moment of action.
VerdictExcellent as a layer on top of 03 or 04 — "saved filters" is a great feature. Bad as the only organizing model, because silent tagging with no review point is exactly the setup that produces a quietly-wrong library.

06 · Semantic clusters — no vocabulary at all

06

Let embeddings decide the shape

effort Lfully automaticopaque

Embed each deck's tldr + title (Gemini has an embedding endpoint), store the vector, cluster periodically, and have the model name each cluster. The rail shows clusters. No tags, no topics, no decisions. Additionally: "more like this" becomes a first-class navigation move, and semantic search replaces substring search — you'd find the electricity video by searching "how power actually flows", which today returns nothing.

Pros
  • Genuinely zero curation. Nothing to name, confirm, prune, or merge.
  • Semantic search is a real, large upgrade over the current substring match — arguably the best single retrieval improvement available.
  • "Show me more like this one" is a navigation mode none of the other options give you.
  • No vocabulary means no vocabulary drift, no synonym problem, no granularity problem.
Cons
  • Clusters move under you. Add five videos and yesterday's "Systems programming" cluster is now split in two with different names. Navigation you can't build a habit around.
  • Pocketbase has no vector index. You'd store vectors as JSON and brute-force cosine in Python — fine at 300 videos, a real problem later, and it's a hack either way.
  • You cannot express intent. There's no way to say "I want these two things kept apart" because there's no handle to grab.
  • Cluster names are model-generated and often bland or wrong; renaming them re-introduces the vocabulary you were avoiding.
  • Most expensive option, and the least aligned with "I want to be able to manage this myself".
  • Needs a re-clustering job — new infra (cron, or on-add incremental assignment with periodic full rebuild).
VerdictDon't make this your organizing model. Do steal the semantic-search half of it later as a standalone feature — it's independently valuable and doesn't require clustering at all.

07 · The auto-tagger itself

Independent of which model you pick, the classifier has the same design questions. These are the ones that decide whether it feels magic or feels like a mess.

Where it runs

Extend the existing deck call rather than adding a second one. generate_deck() already gets the full transcript and returns JSON; adding topic and tags to the response schema costs no extra latency and no extra API call. The only change is that the backend now needs to know the current vocabulary, so POST /slides takes an extra input — either the frontend sends the vocab it already has loaded, or the backend reads it from Pocketbase directly.

Sending the vocab from the frontend is the smaller change and keeps the backend stateless. Reading from PB in the backend is the better long-term shape, because it's what a background re-tag job would need anyway.

Constrain the model mechanically, not politely

Gemini's structured output supports enums. For the closed Topic tier, don't write "please pick from this list" in the prompt and hope — put the list in the response schema as an enum. Then a hallucinated Topic is impossible rather than unlikely. Tags stay a free string array, but the prompt should rank reuse over invention explicitly:

This version already incorporates the research in §09 — the usage-sorted ordering and tie-break, the 3–5 cap with an allowed empty result, and the video-specific boilerplate clause:

EXISTING TAGS (sorted by usage, most-used first):
  llm×14  agents×9  investing×7  woodworking×6  interview×5  rust×4 …

Rules:
  1. Prefer an existing tag whenever it is a reasonable fit. Reuse beats precision.
  2. When two existing tags fit equally well, pick the one earlier in the list.
  3. Match the exact spelling and casing of existing tags.
  4. Return 3-5 tags. Fewer is fine. An empty array is fine.
  5. Propose a new tag ONLY if no existing tag covers a *central* theme of the
     video — not a passing mention. Put those in "new_tags", never in "tags".
  6. New tags: lowercase, singular, hyphenated, one or two words.
  7. Tag the subject matter only — not sponsor reads, intros, outros,
     "like and subscribe", or asides the video doesn't actually pursue.
  8. Return each tag with a confidence 0-1.

Rule 1 is doing most of the work. Left to itself the model optimizes for descriptive accuracy, which produces a fresh perfectly-apt tag for every video and a vocabulary of size n. You have to explicitly tell it that consistency is worth more than precision. Rule 7 exists because production taggers all need an equivalent — Karakeep's version refuses to tag cookie walls and CAPTCHA pages; yours has to refuse the sponsor segment.

Then don't trust any of it

Measured out-of-vocabulary leakage under a hard "only use these tags" constraint runs around 10%. So after the call: intersect the returned tags against the actual tag table, apply the members, and route the non-members into new_tags where they need a click. The prompt is a strong prior, not an enforcement mechanism — the only genuinely enforced part is the Topic enum, because that one is in the response schema.

Silent vs. suggest-then-confirm

Confirm everything (option 03/04 default)

One extra click per add. In exchange, wrong tags never enter the library, and you build an accurate mental model of your own vocabulary because you see it every time.

Threshold hybrid

Auto-apply existing tags above ~0.75 confidence; show anything lower as an unselected suggestion; always require an explicit click for a brand-new tag. Most adds become zero-click, and the one action that permanently grows your vocabulary stays deliberate.

The asymmetry that matters

Applying a wrong existing tag is a small, reversible error — one video is slightly misfiled. Creating a redundant new tag is a permanent, compounding error — it splits a concept in two forever and every future video has to pick a side. Gate tag creation hard; be relaxed about tag application. That asymmetry should drive the whole UX.

08 · Tag hygiene & backfilling what you already have

Any tag-based option needs these three things or it rots. They're small individually, and skipping them is the most common way tagging systems die.

  • Merge & rename. With a tags collection this is trivial — rename is one record update and every video follows automatically; merge is "repoint relations from A to B, delete A". Do this as a relation collection rather than a JSON string array precisely so you get this for free. This is the single strongest argument against storing tags as a JSON array on videos.
  • An orphan view. "Tags used once" and "videos with no tags" as two clickable rail entries. Cleanup you can actually see the end of.
  • A promote path. When a tag crosses ~15 uses, surface it: "you have 17 videos tagged agents — promote to a Topic?" Your taxonomy should be allowed to learn from your behaviour instead of being fixed on day one.

Backfilling the existing library

Whatever you pick, you have an existing pile to classify. The transcripts and decks are already stored, so this costs Gemini calls but no re-fetching. Two honest ways to do it:

  • Bootstrap-then-tag (better). First pass: send the model 30–40 tldrs at once and ask it to propose a starting vocabulary of ~15 tags and ~8 Topics. You edit that list. Second pass: tag every video against the vocabulary you just approved. This produces a coherent vocabulary because the model saw the whole corpus before naming anything.
  • Sequential (worse). Tag videos one at a time, vocabulary growing as you go. The first 20 videos get tagged against an almost-empty vocabulary and end up with idiosyncratic tags nothing else ever reuses.

Given your preference for choosing at the moment of action rather than accepting a hardcoded default, the bootstrap pass should end in a review screen where you rename, merge, and delete before a single video is touched.

09 · What the field actually does

A survey of the PIM literature and of what shipping products actually do — including two self-hosted apps that already solved almost exactly your problem. Three findings changed my recommendation; they're flagged in the callout at the end.

The empirical baseline is uncomfortable: folders beat tags

Bergman et al. ran two studies (Gmail, n=75, plus a file-system study) on folder-vs-tag preference in personal information management. The result is blunt: a strong preference for folders over tags for both storage and retrieval. In the minority of cases where people tagged at all, they typically applied a single tag per item — using tags as folders. Multi-classification was "only marginally used for retrieval", and tag-based retrieval was both slower and less successful.

The stated cause: a 1→1 mapping ("item a is in folder x") is easier to remember than 1→many ("item a is reachable via x, y, or z"). A companion paper is titled, accurately, "Tagging personal information: A contrast between attitudes and behavior" — people say they prefer tagging, then don't do it.

What this means for you

If tagging is manual, you largely won't do it, and when you do you'll apply one tag. This is not an argument against tags — it's an argument that tags are only viable when a machine applies them, and that you still need a small, memorable, one-per-item backbone for navigation. Which is precisely the shape of option 04.

is.biu.ac.il/sites/is/files/Folders%20vs%20Tags%20-%20Preprint%20version.pdf

Everyone converges on the same three layers

Zotero, Karakeep, Raindrop, Capacities and Notion all independently land on the same split:

LayerCardinalityJob
Collections / lists / locationsfew; one or a handful per itemCoarse, durable "where does this live"
Tagsmany; multi-valuedCross-cutting themes — the auto-taggable layer
Saved searches / smart listsunlimited; zero costThe actual browsing UI, as rules over the two above

Capacities states the boundary most crisply: "Use collections to group content within the same object type. Use tags to group content across different object types." The Zotero community line is "maximise tags and minimise sub-collections, and make full use of Saved Searches."

Also worth knowing: Zotero's collections are hierarchical and non-exclusive — the same item can sit in several collections at once. That's a fourth model I hadn't considered: hierarchy without the one-home constraint. It weakens option 02's central objection, at the cost of the thing that made folders memorable in the first place.

The two closest pieces of prior art

Karakeep (self-hosted bookmarks, LLM auto-tagging) and Linkwarden (same category) have both already built the thing you're describing. Their mechanics are worth copying almost verbatim.

Karakeep — silent auto-apply, made safe by provenance

  • Every tag attachment row carries attachedBy: 'ai' | 'human'. The UI splits into Your Tags / AI Tags / Unused Tags. Re-tagging deletes only the AI rows and re-attaches — so re-running the classifier is idempotent and never destroys your own work.
  • Tag identity uses a normalized generated column: lower() then strip spaces, hyphens and underscores. Machine Learning, machine-learning and machine_learning collapse to one tag at the database level. (It does not handle singular/plural — nobody does, and everybody suffers for it.)
  • It does not send the whole vocabulary. It embeds the new item, pulls the top-10 nearest-neighbour bookmarks above 0.75 similarity, takes their distinct tags, sorts shortest-name-first and truncates the joined list at 1000 characters. Prompt cost stays flat as the library grows.
  • Tag style is a user setting injected into the prompt (lowercase-hyphens, titlecase-spaces, …) — casing drift fixed at generation time as well as at storage time.
  • Ships a Cleanups page that detects probable duplicate tags and offers merges, plus deleteUnused() for orphans.
  • Its prompt has a whole clause for refusing to tag Cloudflare pages, cookie walls and login interstitials. Video analogue: sponsor reads, intros, "like and subscribe".

Linkwarden — tagging mode as an explicit user setting

Three modes the user picks between: predefined (a list you wrote), existing (your current tags only), generate (free invention). The existing prompt is the most transferable artefact in the whole survey:

EXISTING TAGS (sorted by usage): {tags}
1. Output ONLY a JSON array
2. Select 3-5 tags from the existing tags above
3. Prefer frequently-used tags (earlier in the list) when equally relevant
4. Match the EXACT capitalization from the existing tags
6. If no tags match well, return fewer tags (minimum 1)
7. Do not create new tags - only reuse existing ones

Line 3 is a free anti-sprawl prior costing one ORDER BY. I had counts in my prompt sketch but not the instruction to break ties toward the frequent ones.

Raindrop's policy is stricter than mine — and they explain why

"We ensure that suggestions are based only on the collections and tags you've already set up — we don't generate new ones like some other services might, as those tend to be too generic and not as useful."

Raindrop never invents. Suggestions are pre-filled into the save form; you deselect and save. They handle cold start with an explicit message telling you to create a few tags first, and newly created tags become eligible immediately. Their newer assistant follows the same rule: "Stella suggests changes — you review and approve before anything is applied." They also have a batch "organization tips" page for retro-organising an existing library as a review surface rather than a background job.

Documented failure modes

Auto-tagging

  • Out-of-vocabulary leakage ~10% even with a hard "ONLY use these tags" constraint (measured: 0.470 for zero-shot LLaMA 1, 0.100 for LLaMA 2). You must validate output against the DB — the prompt constraint is not a guarantee.
  • Category inflation — models over-assign in large taxonomies. Every production prompt caps at 3–5 and permits an empty result.
  • Granularity drift from partial cues: "context over-generalization" measured at 29.8% of errors, "inferential overreach" at 26.9%. For a transcript-based summariser this predicts tags derived from a 30-second tangent in an hour-long video.
  • Markdown-fenced JSON from smaller models is a real filed bug in Linkwarden. Use structured output and write the tolerant parser. Your gemini.py already has _strip_fences — that instinct was correct.

Abandonment

  • Forte's five reasons tagging dies: poor memorability, decision fatigue, lack of concreteness, cataloguing-instead-of-doing, and "requires perfect compliance or information gets lost."
  • Zotero users' recurring regret: "it's hard to make wholesale changes to tags once you have a large library" — build merge/rename before the vocabulary grows.
  • Ban date tags (q3-2024) — they age into noise. Ban person tags (for-katie) — those are bookmarks, not tags.
  • Only ~10% of users find tag suggestions helpful, and ~1 in 3 accepted tags come from suggestions. Suggestions also measurably compress the long tail of the vocabulary — which is what you want here, but it means genuinely novel topics get suppressed. Keep an explicit "none of these fit" escape.

Where the research contradicted me

Three changes to what I wrote above
  1. Topics should be a flag on tags, not a separate collection. Shopify's smart-collection model resolves the "when does a tag graduate into a Topic?" question by dissolving it: a collection is a saved view whose predicate is a tag. So instead of topics and tags as two tables, use one tags table with kind: 'topic' | 'tag'. Promotion becomes a flag flip instead of a data migration, the Topic enum is still just SELECT name WHERE kind='topic', and §08's "promote at 15 uses" button becomes one UPDATE. Strictly better than what I proposed, same UX.
  2. Track tag provenance from day one. I completely missed this. Karakeep's attachedBy: 'ai' | 'human' is the mechanism that makes auto-tagging safe: it gives you bulk-revert, a "review what the AI did" surface, and idempotent re-tagging that never clobbers your own edits. Retrofitting it later means you can't tell which tags you chose. It costs one field.
  3. My "structurally impossible" claim was too strong for tags. It holds for the Topic enum — a response-schema enum is enforced by the API. It does not hold for the free-form tags array, where measured out-of-vocabulary leakage runs around 10% even under a hard prompt constraint. Validate every returned tag against the DB before applying it, and route non-members into the "new tag, needs confirmation" bucket rather than silently creating them.

Two smaller corrections: bump the tag cap from my 2–4 to 3–5, and explicitly permit an empty array (universal across both self-hosted implementations). And add a boilerplate exclusion clause to the prompt — the video-native version of Karakeep's cookie-wall refusal is sponsor reads, intros, outros and "like and subscribe".

Where it agreed

Two-pass retro-tagging (seed batch → human curates the vocabulary → constrained pass over the rest) is exactly what §08 argues, arrived at independently. Suggest-then-confirm gated on tag creation specifically is Raindrop's policy taken one step looser. The 6–12 label cap matches the ~8 Topics I proposed. And "start broad, split later only when volume demands it" (Stack Overflow's tag-sprawl guidance) is the same principle as the promote-at-threshold path.

One structural idea worth stealing outright

Readwise Reader splits Feed (pushed, subscription-sourced, Unseen/Seen) from Library (curated, Inbox/Later/Shortlist/Archive) as two separate locations, not one list. Jellyfin makes the same argument at the library level and warns that mixing content types degrades automatic metadata enrichment.

That's the answer to your dormant subscriptions feature: when you switch it on, subscription-pulled videos should land in a separate Feed location that you triage into the library, not get interleaved into the main list. It also keeps the rail's two axes honest — who made it (channel) and what it's about (Topic) are different questions and should never share a section.

10 · Recommendation

Build option 04 — one closed Topic plus open tags — with the threshold-hybrid tagging policy, and do the option 01 status/star/sort work as its foundation.

The reasoning in one paragraph: you have genuinely unrelated subject areas, which is the case folders are good at, and you already have crossover material, which is the case folders are bad at. Two tiers let you take the win from each without inheriting either failure mode. The closed Topic list gives the rail a permanent shape — the thing a flat tag list can never give you — while open tags absorb all the specificity and all the model's enthusiasm, in a place where sprawl is a nuisance rather than a navigation failure. And because the Topic enum is enforced in Gemini's response schema, the one part of the system that must stay stable is stable by construction, not by prompt discipline.

The survey in §09 didn't overturn this — the Bergman result (people won't hand-tag, and when they do they apply one tag) is an argument for a machine-applied tag layer sitting under a small memorable backbone, which is what two-tier is. But it did improve the implementation in three ways, folded in below.

What I'd build, in order

  1. Migration + status/star. One tags collection with kind: 'topic' | 'tag' and a norm column (lower(), strip space/-/_, unique). Add videos.topic, videos.tags, videos.tag_source, videos.status, videos.starred. Stop hardcoding them in recordToVideo(). Replace the fake CHANNELS rail with real lenses. This alone makes the current list usable and it's the smallest useful commit.
  2. Seed the vocabulary from what you already have. One-off script: feed all existing tldrs to Gemini, get back a proposed ~8 Topics and ~15 tags, review and edit that list yourself before anything is written. This is the step that decides whether the vocabulary is coherent, so it's worth being the one manual step.
  3. Backfill. Batch-classify the existing library against the approved vocabulary. Land results in a review screen, not straight into the DB. Everything it writes is marked ai, so a bad run is one bulk-revert away.
  4. Wire the tagger into /slides. Extend the deck response schema with topic (enum, built from kind='topic') and tags + confidences. Pass the vocabulary usage-sorted. Intersect the response against the tag table before applying. Add the suggestion chips to AddVideoDialog with the threshold-hybrid policy.
  5. Two-tier rail. Topics on top, tags scoped to the selected Topic below — mock 04a.
  6. Tag manager. Merge / rename / delete / orphans, plus the kind flip for promotion — mock 08. Small, but it's what keeps step 4 from rotting, and Zotero users' recurring regret is that they built it too late.

Three changes from the research

  • One table, not two. kind: 'topic' | 'tag' instead of separate topics and tags collections. Promoting a tag to a Topic becomes an UPDATE rather than a migration, and the Topic enum is still just a filtered select. Shopify's smart-collection model, applied.
  • Provenance from day one. Record whether each tag was applied by you or by the model. It's what makes re-running the tagger safe, gives you a "review what the AI did" surface, and makes a bad batch revertible. Costs one field now; unrecoverable if you skip it.
  • Validate, don't trust. The Topic enum is enforced by the response schema. The tags array is not — check every returned tag against the DB and route strangers into the confirm bucket.

What I'd deliberately not build yet

  • Saved views (05) — but sooner than I first said. The research ordering is views before rules before hierarchy, because views are pure derived state with zero blast radius. I'd still not build the full rule-builder UI up front; I'd ship the one-line version — "pin the current filter to the rail" — which with the kind flag is literally what a Topic already is. Full query builder once you've felt which filters you keep retyping.
  • Rules that write data. Karakeep has both saved queries and an event-driven rule engine; the split is instructive. Queries for browsing, rules only for things you genuinely want persisted. You don't need the second one yet.
  • Nested Topics. One level. If you find yourself wanting AI / Agents, that's what tags are for.
  • Embeddings (06). Revisit later as semantic search only. Worth noting Karakeep uses embeddings for something smarter than clustering: retrieving the tags of the 10 nearest already-tagged items as the candidate set, which keeps prompt cost flat as the vocabulary grows. That's the version worth building — but not until the vocabulary is big enough that sending all of it is actually a problem, which for you is a long way off.
  • Merging subscriptions into the Topic rail. The rail currently pretends to be a subscription list. Don't half-migrate it — who made it and what it's about are different axes, and merging them is how the rail got confusing in the first place. When you do switch subscriptions on, copy Readwise: pulled videos land in a separate Feed location with Unseen/Seen, and you triage them into the library. They should never interleave with things you deliberately added.
If you'd rather do less

The honest smaller version is 01 + 03: lenses, plus flat tags with suggest-then-confirm, and skip Topics entirely. You lose the browsable backbone and you'll need the tag manager sooner, but it's meaningfully less code and it upgrades cleanly into 04 later — adding a topic relation on top of an existing tag system is additive, not a migration away from anything. If the two-tier version feels like too much for now, this is the version that doesn't paint you into a corner.
